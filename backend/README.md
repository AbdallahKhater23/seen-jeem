# Seen Jeem Trivia Backend

FastAPI + SQLite trivia engine for the Seen Jeem React/Zustand TV game. The
backend owns the question bank, match allocation, reservations, rerolls, power
ownership, scoring, and synchronisation state. The React app keeps its
presentation layer and talks to the API through a single adapter.

## Content and capacity: what is actually guaranteed

The production bank is honest curated content plus explicitly labelled
procedural puzzles. It is **not** large enough to guarantee 100 repeat-free
matches for arbitrary six-category selections:

- The smallest buckets are `arab_ftbl` (9 / 13 / 19), `general` (18 / 20 / 9),
  `numbers` (9 / 11 / 16), and `football` (13 / 19 / 10). Those are below the
  operational minimum for a full bucket set, so the seeder raises rather than
  inventing rows.
- `flags`, `capitals`, and `clubs` hold 100 per difficulty; `career` holds
  82–100; `worldcup` 56; `ucl` 69/138/69. All are under the 201-per-bucket gate.
- Only `riddles` (240 per difficulty) and `spotdiff` (876–888 per difficulty)
  clear both the 120 floor and the 201 capacity gate with real generated
  puzzles.
- The football ratio is computed from an explicit `football_scope` tag on every
  classified fact. The current aggregate is 1,104 global / 41 Arab facts =
  3.58 % Arab, short of the 85/15 target.

Consequences, stated plainly:

1. **A production 100-match guarantee is not claimed.** `tests/test_100_matches.py`
   verifies the *selector* on an isolated fixture that adds 240 labelled
   `test_fixture` rows per bucket (8,640 synthetic rows, never seeded into
   production). That test creates and fully resolves 100 consecutive matches,
   resolves 3,600 distinct question IDs, asserts zero ID repeats, zero fact-group
   collisions inside each 54-row allocation, and `times_played` only for played
   tiles.
2. The same test asserts that the *real* bank fails the gate and reports the
   missing buckets, so the shortfall cannot silently regress into a false claim.
3. Growing to the 7,236-record universal gate requires more verified curated
   facts (or more legitimate procedural categories), not duplicated questions.

## Quick start

### Accounts and question history

The game now opens with an Arabic username/password registration and login screen.
An account is automatically attached to every match created through the frontend;
players do not need to select their own profile. Passwords use salted scrypt hashes,
and login sessions use revocable HttpOnly cookies lasting up to 30 days.

Opening a question records it in `user_question_history` for that account, including
questions opened in subsequently abandoned matches and replacement questions shown
by a reroll. Future match allocation excludes that account's recorded question IDs,
including after a deck reshuffle. If too few unseen questions remain, creation fails
with `INSUFFICIENT_QUESTIONS` instead of recycling seen questions. Unopened reserved
questions are not counted as seen.

The account header includes a question counter and **سجل أسئلتي** with paginated
history. Logging out does not delete history. Signing in from another browser or
device connected to this same backend uses the same stored history. Accounts on a
shared browser have separate histories. Local saved match recovery is cleared when
switching accounts to avoid resuming someone else's game.

Existing passwordless profiles remain optional local guest profiles; they cannot be
claimed as accounts without proof of ownership. Choose a new username when creating
an account. Password recovery/email verification are not implemented; the signup
screen tells players to keep their password.

Account APIs are `/api/v1/auth/register`, `/login`, `/logout`, `/me`, and `/history`.
Mutating account requests require `X-Requested-With: SeenJeem`. The frontend requires
an authenticated session before creating a match; legacy direct API integrations can
still create installation-based guest matches. Serve the UI and API through the same
origin (the existing Vite/Nginx proxy does this). Use HTTPS with `APP_ENV=production`
for Secure session cookies. Accounts and history live in the existing SQLite database;
no external account service is required.

category/difficulty bucket), and the current `draft` state.

### Category badge

`eligible_count` is computed server-side. It counts active, non-backup questions
that are not used in the bucket's current cycle and are not attached to an
unplayed tile of an *active* match. An active reservation therefore reduces the
badge, and the badge and selector use the same eligibility rules.
`capacity_100_matches` is true only when all three difficulties of that category
hold at least 201 eligible rows.

## Match allocation and selection

- Each match selects exactly six distinct category slugs.
- For each of those 6 categories × 3 difficulties, creation allocates **2
  primary questions and 1 backup**: 36 primaries + 18 backups = 54 records.
- All 54 question IDs and all 54 `fact_group_id` values must be distinct within
  one allocation; the whole allocation succeeds or fails atomically.
- **Layer 1 — casino shoe:** each `(category, difficulty)` bucket has a
  Fisher–Yates-shuffled `deck_position` produced at seed time (deterministic for
  an explicit seed, random salt in normal operation). Eligible rows are taken in
  shoe order, and a bucket reshuffles only when its eligible cycle is exhausted.
- **Layer 2 — usage:** selecting or reserving never increments `times_played`.
  Resolving a tile records one `question_usage` row for the bucket cycle and
  increments `times_played` exactly once. Replaced/unplayed primaries and unused
  backups do not count as played.
- **Layer 3 — fact cooldown:** hard rule is unique `fact_group_id` across the
  whole 54-row allocation. Soft rule avoids fact groups resolved in the five
  most recent *completed* matches; it is relaxed only when fewer than three
  hard-valid candidates remain in a bucket, and every hard constraint still
  applies.
- Reservations are released when a match is abandoned, when a tile is abandoned
  before play, and for unused backups when the match completes.
- Every write runs inside `BEGIN IMMEDIATE` with optimistic `expected_version`
  checks and idempotency records, so duplicate requests cannot double-score,
  double-count usage, or produce a second replacement for one reroll.

## Identity, exposure history, and the anti-repeat engine

### Three identity scopes

| Scope | Row | Purpose |
| --- | --- | --- |
| Player profile | `users(kind='named')` | One person, follows them across devices. Unique `username`. |
| Installation | `device_installations` | One app install on one device/browser profile. Owns a **shadow** user (`users(kind='shadow')`). |
| Participation | `match_participants` | Which profiles are in a match and on which team. |

`device_installations.credential_hash` stores only a SHA-256 hash of a
server-issued, high-entropy, random credential; the raw credential is returned
once at registration and never again, never logged, and never exposed by any
endpoint. There is no canvas/font/user-agent/IP fingerprinting: the
installation is exactly as durable as the credential the client keeps.

Registering an installation is idempotent per `Idempotency-Key`, and the
credential is bound server-side to one persistent shadow user, so a
profile-free player keeps one identity across restarts and session renewal.

### Effective identity set

Every match is hosted by exactly one installation (`matches.host_installation_id`,
required for match creation). The **effective identity set** of a match is:

```
match_participants.user_ids  ∪  { host installation's shadow_user_id }
```

A question is ineligible for a match if *any* member of that set has already
been exposed to it. So a question seen by one participant is excluded for the
whole group, a question seen on the device is excluded for everyone who later
plays on that device, and a question seen by a profile is excluded wherever
that profile plays. Identical identities are de-duplicated before any query.

`user_question_history` enforces `UNIQUE(user_id, question_id)` in the
database — application-level checks alone are not relied on.

**Outcome values.** The history outcome column reuses the application's real
answer lifecycle — `team1` / `team2` / `none` — exactly like
`match_tiles.outcome`, rather than a separate `correct` / `incorrect` /
`skipped` vocabulary. The app has no "skipped" state: an abandoned tile is
released and never exposed. Inventing a second vocabulary would have split the
meaning of "outcome" across two tables, so the existing one was kept.

**No rate limiting on the identity endpoints.** The project has no established
rate-limiting convention (no limiter middleware, no dependency, no
`Retry-After` handling), so `POST /users` and `POST /installations/register`
follow the same open-host policy as the rest of the API. Adding a limiter
would have meant a new dependency and a new convention rather than following
one; on the intended local-network deployment the exposure is limited to
creating rows. If the service is ever exposed to the internet, both endpoints
need a real limiter before that decision is revisited.

### Exposure is a specific event

Exposure is recorded when the question becomes **visible**: the moment a tile
is opened (`open_tile`), or when a reroll swaps in a backup that the players
see. It is *not* recorded when a question is merely reserved at match
creation, and an unused backup is never recorded. Outcomes are updated later,
when the tile is resolved. A repeated open for the same match is a safe no-op;
an exposure for the same question from a *different* match fails closed with
`HISTORY_CONFLICT` rather than being silently swallowed.

History rows survive match deletion (`match_id` is `ON DELETE SET NULL`) and
question deletion is blocked (`ON DELETE RESTRICT`), so anti-repeat evidence
cannot be erased by ordinary application cleanup.

### Selection is atomic and history-aware

`selector.eligible_questions` adds one `NOT EXISTS` clause over
`user_question_history`, parameterised with a generated placeholder list, and
drops the clause entirely when the identity list is empty (an empty `IN ()`
would silently disable the filter). The whole match — identities, eligibility,
selection, match row, participants, and 54 allocations — is created inside a
single `BEGIN IMMEDIATE` transaction, so a concurrent creator cannot take the
same question: the reservation in `match_tiles` becomes visible before the
transaction commits.

When a bucket cannot supply the required primaries/backup, the transaction
rolls back entirely — no partial match, no orphan tiles — and the API returns
the domain error (`INSUFFICIENT_QUESTIONS`, with the bucket and the
required/available counts) instead of falling back to a question the
participants have already seen.

### Measured query behaviour

`scripts/perf_history_probe.py` runs the eligibility query against a copy of
the production database and prints the SQLite plan at several history sizes:

| History rows | Bucket eligibility query | Plan |
| --- | --- | --- |
| 0 | 1.13 ms | `SEARCH q USING INDEX idx_questions_cat_diff_active` + `CORRELATED SCALAR SUBQUERY` → `SEARCH h USING COVERING INDEX sqlite_autoindex_user_question_history_1 (user_id=? AND question_id=?)` |
| 5 000 | 1.25 ms | same |
| 50 000 | 0.96 ms | same |
| 200 000 | 1.13 ms | same |

The history filter is a correlated point lookup on the `UNIQUE(user_id,
question_id)` autoindex — a covering index, so the history table is never
scanned — and the timing is flat from an empty history to 200 000 rows. That
is also why no extra index was added on `user_question_history`: the
uniqueness constraint already provides the required access path.

### Residual limitations (stated, not hidden)

- The installation credential is a bearer token in `localStorage`; an XSS
  payload or a user with devtools can copy it, and clearing site storage
  creates a *new* installation identity. Device-level anti-repeat protection
  is therefore exactly as durable as that credential.
- A named profile is selectable by anyone at the device (shared-TV trust
  model); profile choice is not authentication.
- There is no history-reset or bypass endpoint, by design: any administrative
  override would weaken the primary invariant.

## Content pipeline

`app/data/` holds curated registries: 100 countries, clubs, career paths, UCL
finals, World Cup tournaments and facts, Arab/Khaleeji football, records, and
general knowledge. `app/services/content.py` stores facts first (with
`fact_group_id`, `source_entity_id`, `verification_status`, `content_version`,
and provenance) and compiles questions from validated fields with documented
difficulty rules (200 = widely known, 400 = venue/runner-up/less obvious,
600 = precise historical detail).

`generated_puzzle` covers two deterministic families:

- **Riddles** — 240 sequence, 240 proportion, and 240 age puzzles per
  difficulty, each a distinct `fact_group_id`.
- **Spot the difference** — 12 scenes × 220 three-anchor combinations, each
  payload carrying `sceneId`, `sceneVersion`, `variantSeed`, 12 `anchors`, 3
  `mutations` (keyed by anchor id), and 3 `differences`. Difficulty is derived
  from anchor size, position, and mutation type. Re-running the compiler yields
  the same identities.

Validation rejects empty questions/answers, unknown categories/difficulties,
missing fact groups, invalid flag codes, career payloads with fewer than two
stops, spotdiff payloads without 3 differences / 12 anchors / matching anchor
IDs, and duplicate normalized question keys. Question identity is the SHA-256
fingerprint; facts and questions are separate identities.

### Difficulty rubric (200 < 400 < 600, per category)

Difficulty is two-axis: **question task** × **entity fame** for an Arab
casual-to-fan audience. 200 = known to casuals, 400 = known to followers of
the category, 600 = expert/record detail. The selector trusts the label
blindly (2 primaries + 1 backup per bucket, points = difficulty), so the
label must be right at seeding time:

- **Puzzles (objective):** riddles sequence → proportion → age algebra;
  matchstick 1-digit → 2-digit incl. × → 2-move (validated); spotdiff by
  measured subtlety score, sorted into thirds.
- **Fan knowledge (fame-calibrated):** nicknames by Wikidata sitelinks into
  thirds; technology/videogames admit only the top-120 by sitelinks (obscure
  entities excluded rather than mis-tiered); harvested long-tail flags by
  verified API population (≥20M → 200, ≥1M → 400, <1M → 600, unknown → 200
  without claiming difficulty). The curated 100-country list is itself the
  audience-known set, so its template tiers stand.
- **Curated trivia:** country beats league (clubs 400 = country, 600 =
  league), winners/hosts at 200, runner-ups/venues at 400, exact scores and
  record-holders at 600; one-off 2022-final facts sit at 200, not 600.
- **Convergence:** re-running the seed updates the difficulty of rows whose
  tier changed (`updated` count in the report and `seed_runs`), and rebuilds
  deck order for old and new buckets — tier fixes reach existing databases
  instead of freezing the old labels forever.

`tests/test_difficulty_tiers.py` pins the rubric: clubs order, World Cup
record placement, harvester population bands, and seed convergence.

### Harvesting and sync

`seed_harvester.py` and `app/services/harvester.py` use `httpx.AsyncClient` with
bounded concurrency, explicit timeouts, retries, and a `.seed_cache/` with a
24-hour TTL. RestCountries requests the ISO/name/translation/capital/region/
population/borders/currencies/UN fields; Wikidata uses `ORDER BY ?player LIMIT/
OFFSET` (integer offset, no placeholder bindings) and stores its rows as
`needs_review` facts rather than auto-generating questions. Failures are
non-fatal: existing rows stay intact and the report names the unavailable
source.

`POST /pool/sync` records a `sync_jobs` row (`queued`, `running`, `succeeded`,
`partial`, `failed`), refuses a duplicate active job for the same source, and
executes via `BackgroundTasks`. This is **not** a durable queue: a process
restart fails the job and the API reports `durable: false`; it never claims a
completed harvest when only a job was queued. Low inventory is surfaced by match
creation errors (`INSUFFICIENT_QUESTIONS` with the affected buckets) rather than
by blocking on network calls.

## Frontend integration

`backend/integration/frontendAdapter.js` is the only contract boundary:

- categories: backend `spotdiff` ↔ UI `spot`;
- question types: `text` ↔ `standard`;
- teams: `team1/team2` ↔ `team-falcons/team-wolves`;
- outcomes: `team1/team2/none` ↔ `active_team/defending_team/nobody`;
- tile keys: `spotdiff-…` ↔ `spot-…`;
- board, resolve, reroll, and draft responses mapped into Zustand shapes.

The lobby loads the real 12-category catalogue and its eligible counts, allows
exactly six selections, offers `اختيار عشوائي (6 فئات)`, and creates the match
on the server before advancing. The board renders only server tiles and resolves
category names/icons from the server catalogue (the catalogue is preserved when
the store leaves the lobby). The arena renders backend questions, including
`payload.sceneId`/`anchors`/`mutations`/`differences`, and commits server results
rather than optimistically marking a tile played. Failed writes keep the cached
board visible and surface an Arabic error; localStorage remains a recovery
cache, not the authority for a match that has a `match_code`.

## Database and concurrency

- The live schema version is `SCHEMA_VERSION` in `app/schema.py` (7 at the time
  of this writing; it rises with every additive migration). It holds 12
  categories, fact records, usage/cycles, 54-row allocations, server-owned
  `match_powers`, question sessions (`opened_at`, `revealed_at`, `active_team`,
  `noise_until`), sync jobs, harvester cursors, plus the identity tables
  (`users`, `device_installations`, `match_participants`,
  `user_question_history`).
- Migrations are additive: v1 → v2 backfills `fact_group_id` as
  `legacy:<fingerprint>` and preserves rows; v2 → v3 adds session columns;
  v3 → v4 adds `match_powers`; v4 → v5 adds `matches.host_installation_id`
  and creates the identity tables; v5 → v6 adds the account/session tables;
  v6 → v7 adds the provenance columns. A future schema version fails closed.
- WAL, `foreign_keys = ON`, `synchronous = NORMAL`, 5 s busy timeout, short-lived
  connections, and `BEGIN IMMEDIATE` for every multi-step write.
- Unique constraints/indexes cover category slugs, question fingerprints, tile
  keys, bucket cycles, `(match_id, request_id)`, and idempotency keys.

## Known gaps and risks

- **Capacity:** the real bank does not meet the per-bucket 201-question gate, so
  a universal 100-match guarantee is unproven and unclaimed. The 100-match test
  proves selector correctness on a clearly labelled synthetic fixture.
- **Football ratio:** measured at 3.58 % Arab vs the 15 % target; more verified
  Arab/Khaleeji facts are needed.
- **Sync durability:** background sync runs in-process and does not resume after
  restart; job rows and text statuses are truthful about this.
- **Powers:** ownership, activation windows, noise/steal/reroll, and score
  effects are server-side; visual countdown presentation remains client-side.
- **Admin dashboard:** it is read-only and token-gated, with no user accounts or
  audit trail for who viewed a page. The token is kept in `sessionStorage`, not
  persisted to `localStorage`.
- **Host-only app:** there is no player authentication beyond the optional admin
  token, and no TLS/reverse-proxy setup.
- **Identity limits:** the installation credential is a bearer token kept in
  `localStorage`; copying or clearing it breaks device-level anti-repeat
  continuity (the old server-side history is kept, but the new installation is
  a new identity). A named profile is not authenticated — on a shared TV
  anyone can select it. There is no account deletion, anonymisation, or
  history-reset path, so deleting a profile is not currently possible without
  direct database work.
